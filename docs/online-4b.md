# Онлайн-партии 4B: места и подтверждённые ходы

## Граница этапа и текущая проверка

Добавлены два места без регистрации, восстановление роли из браузерного токена, серверная проверка хода, атомарное сохранение с `version`, ручное обновление и обработка конфликтов. Realtime, WebSocket, учётные записи, присутствие в реальном времени, часы, анализ и Stockfish в online-режиме не используются.

Код проверен локально с настоящим PostgreSQL/PGlite, реальным обработчиком Edge Function и production-клиентом в Chromium. Migration 4B **не применялась к внешнему Supabase**, Edge Function **не развёртывалась**. Подтверждённое пользователем облачное развёртывание 4A не является проверкой 4B. Для работы новой записи ходов в облаке нужны оба артефакта 4B; одной migration недостаточно.

## Идентификация

`PlayerIdentityStore` генерирует 32 случайных байта через `crypto.getRandomValues` и хранит 64-символьный hex-токен под ключом `online-chess:seat:<game-id>` в `localStorage`. Game ID создаётся через `crypto.randomUUID`; credential сохраняется **до** запроса создания или join, чтобы не потерять его при смене страницы после ответа сервера.

На сервер токен передаётся только в теле HTTPS POST. В URL, отображаемый UI, публичную запись, логи приложения или Git он не попадает. БД хранит `sha256(UTF8(token))` как 32-байтный `bytea`. Высокая энтропия случайного токена делает отдельную соль необязательной; это bearer credential, а не пользовательский пароль.

На каждом открытии страницы роль проверяет сервер: локальная запись цвета не считается авторизацией. Повреждённый локальный токен удаляется; корректный по формату, но не признанный сервером токен тоже очищается. Отсутствие ключа означает просмотр или возможность занять действительно свободное место. Если оба места заняты, знания ссылки недостаточно для игры. Если localStorage недоступен, создание/join не выполняются; небезопасной подмены на временную память нет.

Повторное открытие в том же браузерном профиле восстанавливает роль. Два профиля имеют разные ключи; две вкладки одного профиля считаются тем же игроком. При потере ключа занятое место не восстанавливается автоматически. Скопировавший credential получает права этого места, поэтому нужны HTTPS и защита приложения от XSS. Отзыва/ротации/срока действия ключа и переноса на другое устройство пока нет.

## Схема и совместимость

Migration: `supabase/migrations/202610160002_online_seats_and_moves.sql`, поверх неизменённой migration 4A.

Добавлены:

- `creator_token_hash`, `opponent_token_hash` — закрытые credential hashes;
- `creator_joined_at`, `opponent_joined_at` — моменты резервирования мест;
- `updated_at` — последнее изменение записи (для старых строк первоначально время migration).

Constraints связывают наличие hash и времени места, проверяют длину hash и запрещают одинаковые ключи у двух мест. Колонка `version` остаётся прежней, но теперь изменяется сервером. Первое присоединение второго игрока увеличивает её на 1, каждый успешный ход — ещё на 1; повторный join тем же ключом версию не меняет.

Старые ID, FEN, история, цвет и версия 4A сохраняются. У старых строк нет доказательства владения создателем: они остаются read-only legacy-партиями. Автоматически отдать их первому посетителю было бы захватом места. Для новой игровой партии используется новый endpoint создания. Старый `create_online_game(choice)` остаётся совместимым с клиентом 4A, но создаёт только legacy-записи.

После добавления секретных колонок все публичные ответы переключены на **явную проекцию** `online_game_public`; `to_jsonb(whole_row)` больше не используется. Ни одна публичная функция не возвращает credential hashes.

## RPC

| Функция                                           | Доступ                          | Назначение                                                                             |
| ------------------------------------------------- | ------------------------------- | -------------------------------------------------------------------------------------- |
| `create_online_game_with_seat(id, choice, token)` | anon/authenticated              | Создать партию и закрепить цвет за создателем; повтор с тем же ID/ключом идемпотентен  |
| `get_online_game_session(id, token?)`             | anon/authenticated/service_role | Публичная позиция + проверенная роль текущего ключа                                    |
| `join_online_game(id, token)`                     | anon/authenticated              | Занять противоположный цвет под `FOR UPDATE`; повтор своего ключа возвращает свою роль |
| `get_online_game(id)`                             | anon/authenticated              | Совместимое чтение публичной записи без role/credential                                |
| `commit_online_move(...)`                         | **только service_role**         | Атомарно дописать один уже проверенный доверенным runtime ход                          |

У таблицы по-прежнему включён RLS и отозваны прямые SELECT/INSERT/UPDATE/DELETE для PUBLIC, anon и authenticated. Широких UPDATE-policies нет. Вспомогательные функции projection/hash/role закрыты для публичного исполнения. `SECURITY DEFINER` функции используют пустой `search_path` и квалифицированные имена таблиц.

Join блокирует строку. Создатель со своим ключом всегда получает свой исходный цвет и не может занять оба места. Первый независимый ключ получает противоположный цвет. Следующий получает `GAME_FULL`. Если ответ первого join потерян, повтор с сохранённым тем же ключом возвращает уже занятое им место.

## Authoritative validation: Supabase Edge Function

Полные шахматные правила не дублируются на PL/pgSQL. Выбран бесплатный в пределах квот Supabase доверенный runtime: `submit-online-move` в Deno, использующий тот же `ChessGame` / `restoreGame` и `chess.js@1.4.0`, что приложение.

Поток:

1. Браузер отправляет `game_id`, `player_token`, `from`, `to`, `promotion?`, `expected_version` в **Edge Function**. Готовые FEN, история и заявленный клиентом цвет не принимаются.
2. Функция ограничивает размер тела, проверяет форму команды и загружает авторитетную запись и роль через SQL.
3. Проверяет существование, ключ, занятость второго места и версию.
4. Восстанавливает всю историю в `ChessGame`, проверяет завершение и очередь, выполняет ход через правила. Рокировка, en passant, шах, мат и превращение проверяются библиотекой, а не условиями перемещения в SQL.
5. Только после этого вызывает `commit_online_move` с server-only service role.
6. RPC берёт `FOR UPDATE`, повторно проверяет ключ, оба места, ожидаемую версию и очередь. При совпадении добавляет **один** action в историю, увеличивает `version` на 1 и возвращает публичную сессию.

Если другая операция успела между чтением и commit, версия отличается: запись отклоняется. Клиент один раз перечитывает состояние, сообщает о конфликте и просит выбрать ход заново. Он не повторяет mutation автоматически и не добавляет ход оптимистично. При потере подтверждения после возможного commit тоже выполняется чтение, а не слепая повторная отправка.

**Одна SQL migration не обеспечивает полной шахматной валидации.** `commit_online_move` является закрытым примитивом доверенного backend. Выдавать EXECUTE этой функции браузерным ролям или вызывать её из клиента нельзя. Владельцы БД и обладатели service-role ключа по определению доверены; они могут обходить правила, как и напрямую изменять БД.

`index.ts` получает `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` только из серверного окружения Supabase. Эти значения не добавляются в `.env.example` браузера. Приложение продолжает использовать только публичные `VITE_*` переменные.

В `supabase/config.toml` у этой функции `verify_jwt = false`: регистрации и Auth JWT игроков нет, а publishable key не является player identity. Это не отсутствие авторизации — bearer seat token обязательно проверяется SQL/handler для каждой команды. CORS не является механизмом авторизации; endpoint использует POST без cookie-auth и разрешает browser clients, владеющие credential.

## Архитектура и UI

- `ChessGame` и сериализация — общие правила и история, без Supabase.
- `OnlinePlayerRepository` — network-контракт новых операций; старый read/create interface остаётся для совместимости и независимых тестов 4A.
- `SupabaseOnlineGameRepository` знает RPC/HTTP, но не UI. Для хода вызывает только Edge Function, не закрытый SQL commit.
- `OnlinePlayerService` связывает storage, repository и восстановление ядра.
- `useOnlineGame` управляет load/join/confirmed move, превращением, блокировкой ввода, отменой UI-операций и конфликтами.
- `Board2D` по-прежнему получает снимок, ориентацию, блокировку и действие хода. Никаких SQL, seat-токенов или сетевых клиентов внутри него нет.

До второго места показано «Ожидаем второго игрока». После ручного обновления — «Соперник подключился». Это означает **занятое место**, а не live-presence. У каждого игрока показан его цвет, фигуры ориентированы его стороной вниз. Без роли, до join, во время чужого хода, загрузки/сохранения или после результата ввод закрыт. Для превращения применяется общий диалог выбора фигуры.

## Проверенное локально

- Автотесты правил и восстановления прошлых этапов.
- Реальная migration поверх 4A, сохранность legacy-строк, hashes и отсутствие их в публичных ответах.
- SQL-права anon/authenticated, закрытый commit, роли, идемпотентность, третье место, очередь и сравнение версий.
- Настоящий authoritative handler с PostgreSQL: нелегальный ход, чужие фигуры/ключи, превращение, результат, один append и один increment, гонка двух запросов.
- Browser storage, reload роли, повреждённые ключи, UI запрета ввода, подтверждение и восстановление после конфликта.
- Chromium production: 1440, 390, 320 px, отдельные профили двух игроков и зрителя, ручной обмен ходами, reload, stale-tab conflict, отсутствие переполнения и необработанных JS-ошибок. HTTP-граница Supabase в этом прогоне направлена в локальный PostgreSQL + **тот же** handler. Это не проверка развернутого внешнего Supabase.

PGlite работает на одном соединении. Конкурирующие async-запросы проверяют устаревший snapshot и CAS, но не заменяют многосоединительный нагрузочный тест настоящего PostgreSQL после развёртывания.

Команды:

```sh
npm run typecheck
npm test
npm run build
git diff --check
# При установленном Deno 2:
deno check --config supabase/functions/submit-online-move/deno.json supabase/functions/submit-online-move/index.ts
```

Зависимости Edge Function закреплены в её `deno.json` / `deno.lock`. Для совместного использования доменных модулей runtime-import сериализации явно указывает `.ts`; TypeScript проверяет handler, Deno дополнительно проверяет настоящий entrypoint.

## Развёртывание — только после отдельного подтверждения

1. Проверить, что выбран именно проект Online Chess, а migration 4A уже присутствует. Просмотреть новую SQL migration и сохранить нужную резервную копию/точку восстановления.
2. По отдельному подтверждению применить **только** `202610160002_online_seats_and_moves.sql` поверх 4A. Старую migration заново не выполнять.
3. По отдельному подтверждению развернуть функцию командой `supabase functions deploy submit-online-move --project-ref <online-chess-project-ref>`. CLI использует `supabase/config.toml` с обязательной seat-token авторизацией внутри handler. Server-side URL/service-role key Supabase предоставляет Edge runtime автоматически.
4. Пересобрать/опубликовать web-клиент с публичными URL/key этого проекта.
5. Выполнить отдельный внешний smoke: создать новую партию в профиле A, присоединиться в профиле B, вручную обновить A, обменяться ходами, проверить профиль C, reload, конфликт и отсутствие прямого commit-доступа у anon.

До согласованного развёртывания новые endpoints могут сообщать о неподготовленном хранилище/функции. Никакого fallback на запись из клиента нет.

## Ограничения и 4C

- Ссылка даёт просмотр и возможность первому получателю занять свободное место. Она не удостоверяет человека. Утечка player token даёт права его места.
- Нет recovery/revocation/expiration ключей, rate limiting, CAPTCHA, распределённой защиты от спама и quotas приложения. Для широкого публичного запуска нужна защита create/join/submit от злоупотреблений; бесплатные квоты Edge не безлимитны.
- Если ответ create потерян, credential уже сохранён под ID, но интерфейс пока не показывает список незавершённых созданий. Если ответ move/join потерян, повторное чтение/идемпотентный join восстанавливает подтверждённое состояние.
- Уже выполняющаяся серверная операция может завершиться после отмены браузерного запроса. Защита от дублей — версия/идемпотентность на сервере, а не предположение, что AbortSignal отменил транзакцию.
- Старые 4A-партии сохраняют read-only режим. Нет подмены неизвестного владельца новым посетителем.
- Следующее 4C требует отдельного проектирования чтения Realtime с RLS и **без публикации credential hashes**, порядка обновлений по версии, безопасного resync и присутствия. Нельзя просто включить публикацию всей текущей таблицы с секретными колонками. Публичная проекция или отдельный безопасный канал должны быть спроектированы до подписок.

Realtime и reconnect на этом этапе не реализованы.
