# Этап 4C: Realtime-синхронизация

Код 4C подготовлен и проверен локально. Migration 4C в реальный Supabase не применялась; публикации и настройки проекта не изменялись. По данным пользователя, 4A/4B уже работают в отдельном Supabase-проекте Online Chess.

## Механизм и границы доверия

Используется Supabase **Database Broadcast**, а не Postgres Changes для `online_games`. Триггер отправляет в публичный канал `online-game:<uuid>` событие `version_changed`:

```json
{ "game_id": "<uuid>", "version": 4 }
```

Supabase может дополнить payload техническим UUID `id` сообщения; адаптер допускает этот ключ. Другие поля, неправильный ID партии и некорректные версии отклоняются. Триггер перечисляет поля явно: целая строка, `NEW`/`OLD`, FEN, история, токены и их hashes в канал не передаются.

Событие означает только «перечитай сессию». Состояние и цвет игрока приходят через существующие `OnlinePlayerService` / repository и безопасные RPC. Серверная проверка ходов и владение местом остаются в 4B. Realtime не отправляет mutations и не повторяет ход после сбоя.

Канал публичный, доступен знающему UUID из приглашения, как и просмотр партии. Подписка не требует и не получает seat credential. Это **не защищённый источник уведомлений**: другой клиент может послать поддельную версию. Поэтому версия события не становится подтверждённой версией, не меняет доску или права. Ложный сигнал способен вызвать только ограниченное по частоте безопасное чтение. Для публичного сервиса остаются нужны лимиты API/Realtime; это решение не является защитой от распределённого спама.

## SQL

Migration: `supabase/migrations/202610160003_online_version_broadcast.sql`.

Добавлены:

- trigger function `public.notify_online_game_version()` (`SECURITY DEFINER`, пустой `search_path`, прямой вызов от public/anon/authenticated запрещён);
- trigger `online_game_version_broadcast`: после INSERT или UPDATE `version`, только при увеличении версии для UPDATE.

Новых таблиц нет. Существующий Supabase `realtime.send(jsonb,text,text,boolean)` вызывается с `private = false`. Сигнал отправляется транзакционно через инфраструктуру Supabase. Ошибка уведомления не отменяет корректное сохранение партии: это best-effort доставка, которую дополняет resync.

Migration не меняет RLS, SELECT/UPDATE grants или publication. Перед созданием объектов она проверяет наличие `realtime.send` и отказывается продолжать, если `online_games` включена в `supabase_realtime`. **Таблицу `online_games` публиковать нельзя**, в ней закрытые hash-колонки. Нельзя заменять явный payload на `realtime.broadcast_changes(NEW, OLD)` или JSON всей строки.

## Клиент и порядок версий

`src/features/online/realtime/` содержит контракт `OnlineRealtimeClient`, Supabase-адаптер и независимый `OnlineGameSync`. UI не импортирует каналы SDK. Repository и адаптер используют один экземпляр SupabaseClient; cleanup удаляет только свою подписку, не отключая общий клиент.

`OnlineGameSync` хранит watermark только из подтверждённых RPC/ответов на mutation. Более старая загруженная сессия игнорируется. События старее или равные подтверждённой версии, а также дубликаты ещё не подтверждённых сигналов, не вызывают лишних чтений. Новые сигналы объединяются, одновременно выполняется одно чтение; обычные фоновые чтения стартуют не чаще одного раза в секунду. Память неподтверждённых сигналов ограничена 64 элементами. Даже выдуманная версия из будущего не блокирует настоящую меньшую версию и не вызывает бесконечных попыток её «догнать».

Во время mutation фоновое чтение отменяется/откладывается; успешный ответ подтверждает версию, затем обрабатываются оставшиеся сигналы. Ответ старого запроса не может откатить mutation. При ошибке хода загружается актуальная сессия, сам ход не повторяется. Ручная кнопка и восстановление после ошибки могут обходить секундную задержку.

Снимок той же версии и роли не сбрасывает выбранную фигуру или окно превращения. Смена партии/unmount отменяет запрос, таймеры, listeners и подписку; поздние callbacks старой партии игнорируются.

## Reconnect и пропущенные события

Безопасное чтение выполняется при открытии партии и после каждого успешного `SUBSCRIBED`, включая самое первое: это закрывает промежуток между начальной загрузкой и подключением канала. После ошибки/timeout/закрытия канал пересоздаётся с задержками 1, 2, 5, 10, затем 30 секунд. Успешная подписка сбрасывает backoff и вызывает resync.

Возврат сети и видимой вкладки инициирует reconnect/resync. Дополнительно каждые 30 секунд, когда вкладка видима и браузер считает сеть доступной, выполняется сверка через RPC: так восстанавливаются пропущенные best-effort уведомления даже при формально живом сокете. Фоновые вкладки могут быть заморожены браузером; после возврата выполняется сверка.

UI показывает «Онлайн», «Переподключение…», «Нет соединения». При ошибке фонового RPC сохранённая доска остаётся доступна, появляется подсказка ручного обновления. Кнопка «Обновить позицию» сохранена. Статус «Соперник подключился» означает **занятое второе место**, а не текущий live-presence пользователя. Часы, presence и автоигра за отключившегося игрока не добавлены.

## Включение в реальном Supabase — после отдельного подтверждения

1. Убедиться, что выбран **отдельный Online Chess**, а migrations 4A/4B и Edge Function 4B уже доступны. Использовать существующие публичные `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY`; service-role/secret ключ не должен попадать в браузер.
2. Проверить в SQL Editor наличие Database Broadcast и отсутствие закрытой таблицы в publication (запросы только читают):

   ```sql
   select to_regprocedure('realtime.send(jsonb,text,text,boolean)');
   select pubname, schemaname, tablename
   from pg_catalog.pg_publication_tables
   where pubname = 'supabase_realtime'
     and schemaname = 'public' and tablename = 'online_games';
   ```

   Первый запрос должен вернуть функцию, второй — ноль строк. При другом результате остановиться и отдельно разобраться с конфигурацией. Не включать `online_games` в Realtime publication. Migration сама публикации не исправляет.
3. После подтверждения применить **только новую migration 4C** указанным SQL-файлом или согласованным migration workflow, не переисполняя migrations 4A/4B. Проверить, что проект допускает Realtime Broadcast и публичные каналы (настройка Realtime «Allow public access», если доступна). Если политика проекта запрещает public channels, это решение потребует отдельного изменения проекта или разработки private-авторизации; обходить запрет нельзя. Для Database Broadcast не нужно добавлять `online_games` в Postgres Changes.
4. Пересобрать и опубликовать клиент. Edge Function для 4C изменять/развёртывать не требуется. Разрешить `wss://<project-ref>.supabase.co/realtime/v1/websocket` в CSP/сетевой политике, если такие ограничения используются.
5. В двух независимых браузерах создать новую партию, занять оба места, дождаться «Онлайн», обменяться ходами без ручного refresh. У третьего зрителя не должно быть player credentials; в Broadcast frames должны быть только ID/версия (и технический ID сообщения), без hashes. Проверить offline/online, возвращение из фоновой вкладки и восстановление позиции. Проверить логи Realtime/БД на ошибки отправки и лимиты.

Применение SQL, изменение настроек Supabase и внешний smoke-test в этой задаче не выполнялись. До этого клиент может подписываться, но мгновенные сигналы из БД не появятся; доступно ручное обновление и периодическая сверка. Гарантии доставки, квоты и настройка реального проекта требуют отдельной внешней проверки.
