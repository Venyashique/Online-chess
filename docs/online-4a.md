# Онлайн-партии: этап 4A

## Что реализовано

Создание записи в отдельном Supabase-проекте, постоянный ID, ссылка `/#/online/<uuid>`, чтение записи, восстановление шахматного ядра, доска только для просмотра, история, статус и ручное обновление. Нет Realtime, подключения игроков, отправки ходов, регистрации или Stockfish в online-режиме.

Настоящий внешний Supabase при разработке этого этапа не подключался: отдельный проект ещё не создан. SQL проверен на локальном PostgreSQL через PGlite; HTTP-граница Supabase SDK проверяется тестовыми ответами. Это не подтверждение применения migration или записи в облачную базу.

## Модель данных

Migration: `supabase/migrations/202610160001_online_games.sql`.

| Колонка                     | Назначение                                                                      |
| --------------------------- | ------------------------------------------------------------------------------- |
| `id uuid`                   | Случайный UUID v4, генерируется PostgreSQL, primary key и capability для чтения |
| `created_at timestamptz`    | Время создания на сервере                                                       |
| `initial_fen text`          | Полная исходная позиция с очередью, правами рокировки, en passant и счётчиками  |
| `moves jsonb`               | Упорядоченные действия `{from,to,promotion?}`; по умолчанию `[]`                |
| `creator_color_choice text` | Исходный выбор: `white`, `black` или `random`                                   |
| `creator_color text`        | Окончательный цвет `w`/`b`; случайный определяется один раз при INSERT          |
| `version integer`           | Сейчас 1; резерв для будущего атомарного обновления с проверкой версии          |

Текущие FEN, очередь, шах, статус и результат вычисляются из исходной FEN и истории через `ChessGame`. Цвет второго игрока — противоположный цвету создателя. Эти значения не дублируются в таблице и не могут разойтись с историей. У immutable-записи 4A нет `updated_at`: публичных операций изменения пока нет. Индекс primary key обслуживает единственный запрос — поиск по ID; дополнительные индексы пока не нужны.

Состояния приложения: `waiting` — история пуста, `in-progress` — есть ходы без результата, `finished` — ядро определило завершение. Они описывают сохранённую шахматную позицию, а не факт присутствия двух игроков.

## Сериализация и восстановление

`shared/chess/domain/serialization.ts` не зависит от Supabase. `serializeGame` сохраняет исходную FEN и координатную историю без производных SAN. `restoreGame` проверяет форму данных, создаёт `ChessGame(initialFen)` и выполняет каждый ход через правила. Если ход нелегален, исходная FEN повреждена или есть ход после завершения, загрузка отклоняется с ошибкой.

Так сохраняются SAN-история, очередь, права рокировки, взятие на проходе, превращение и троекратные повторения. Восстановление только последней FEN потеряло бы историю повторений.

SQL constraints проверяют структуру JSON, поля, координаты, превращения, размер истории, соответствие цвета выбору и положительную версию. Они не являются SQL-реализацией шахматных правил. Публичное создание не принимает произвольную FEN/историю: начальная позиция задаётся только серверным default. Запись администратором неподходящей истории будет обнаружена при восстановлении; будущий write API должен отдельно проверять легальность на доверенной стороне.

## Слои

- `OnlineGameRepository` — интерфейс `createGame(choice, signal)` и `getGame(id, signal)`.
- `SupabaseOnlineGameRepository` — единственный online-слой с вызовами Supabase SDK; использует только два RPC, проверяет структуру ответа, обрабатывает ошибки/отмену.
- `OnlineGameService` — проверка ID, обработка отсутствия записи, восстановление ядра и производных полей.
- `useOnlineGame` — загрузка, создание, ручное обновление, ошибка и защита от позднего ответа старого URL.
- `OnlinePage` — UI с внедряемым repository для независимых тестов.
- `Board2D` — тот же renderer, без Supabase и сетевого кода. В 4A ввод заблокирован: изменения не выдаются за сохранённые.

Приложение распознаёт `#/online` и `#/online/<uuid>`. После создания оно переходит на URL и заново загружает запись через repository. Прямая ссылка и перезагрузка работают на обычном статическом хостинге благодаря hash-навигации. Ссылка строится из текущего URL приложения, сохраняя путь развёртывания.

## Доступ и RLS

Таблица включает RLS, а прямые привилегии SELECT/INSERT/UPDATE/DELETE отозваны у PUBLIC, `anon` и `authenticated`. Разрешающих RLS policies нет. Это намеренный запрет прямого API таблицы, а не незаконченная настройка.

Два `SECURITY DEFINER` RPC принадлежат доверенному владельцу migration и работают с фиксированным `search_path = ''`:

1. `create_online_game(p_color_choice)` — проверяет выбор, генерирует запись с серверными default и возвращает её;
2. `get_online_game(p_id)` — возвращает только запись с переданным UUID либо `null`.

EXECUTE этих RPC разрешён `anon` и `authenticated`, общий PUBLIC-доступ к функциям отозван. Нет функции списка, изменения, удаления или присоединения игрока. Вспомогательная функция constraints также не открыта публичному API. Доверенный владелец таблицы обходит RLS внутри этих фиксированных RPC; включать FORCE RLS без отдельного проектирования definer-доступа нельзя.

UUID v4 трудно угадать, но ссылка — **capability для чтения**, а не подтверждение личности. Любой получивший ссылку видит позицию и историю. Цвет создателя не доказывает владение им. Ссылку могут переслать; индивидуального отзыва чтения, разграничения игроков и защиты от спама создания пока нет. Публичный anon/publishable key не секрет и сам по себе не ограничивает злоупотребления: для публичного запуска нужны лимиты/защита создания на серверной границе. Не храните в записи персональные данные или токены игроков.

Этот вариант подходит для первого create/read-этапа: он закрывает перечисление таблицы и произвольную запись, не вводя фиктивную авторизацию. Для 4B нельзя просто выдать `anon` широкие UPDATE-права или принимать от клиента готовую FEN.

## Отдельный проект Supabase: подготовка

1. Создайте **новый** проект с названием `Online Chess` в Supabase Dashboard. Выберите организацию и регион, задайте пароль БД и храните его отдельно. Пароль БД не используется в браузерных переменных.
2. Дождитесь готовности проекта.
3. В диалоге **Connect** либо **Project Settings → Data API** найдите **Project URL** вида `https://<project-ref>.supabase.co`. Это `VITE_SUPABASE_URL`.
4. В **Project Settings → API Keys** скопируйте публичный **Publishable key** (`sb_publishable_…`). Допустим также legacy **anon / public** JWT-ключ. Поместите его в `VITE_SUPABASE_ANON_KEY`: имя переменной осталось таким для обоих поддерживаемых типов публичного ключа. Не берите secret/service_role key.
5. В корне проекта создайте `.env.local` из `.env.example` и заполните две строки. `.env.local` уже игнорируется Git. Все `VITE_*` попадают в клиентскую сборку.
6. Выполните `npm ci`, затем `npm run dev`. После изменения переменных Vite нужно перезапустить; production-сборку — пересобрать.
7. **На этом подготовку остановите.** В рамках текущей задачи migration в реальную БД не выполняется без отдельного подтверждения пользователя. Файл SQL готов к просмотру; когда отдельный проект и переменные будут готовы, можно подтвердить применение именно к нему.

До применения migration создание вернёт понятную ошибку о неподготовленном хранилище. После отдельно согласованного применения можно проверить создание, ссылку и восстановление на реальном Supabase. Сохраняйте номер migration в истории развёртывания; повторный запуск SQL поверх уже созданных объектов намеренно не маскируется `IF NOT EXISTS`.

Если работа идёт в облачной среде с ограниченным исходящим доступом, добавьте **точный hostname нового проекта** (`<project-ref>.supabase.co`) в разрешённые домены. Входящий доступ браузера и исходящий доступ тестовой среды — разные пути. URL неизвестного проекта не подставлялся и сетевые разрешения на другие проекты не добавлялись.

## Проверки

```sh
npm run typecheck
npm test
npm run build
git diff --check
```

Тесты включают реальное выполнение migration в PGlite, RPC под ролями `anon`/`authenticated`, запрет чтения/записи таблицы, защиту RLS даже при случайной выдаче SELECT, SQL constraints, SDK с HTTP mock, repository/service, сериализацию/восстановление, UI и URL. Внешняя Supabase-БД для тестов не нужна. PGlite и `@types/node` — только devDependencies и не входят в браузерное приложение.

Браузерный прогон на 1440/390/320 px использует тестовый HTTP-слой перед локальным PostgreSQL/PGlite с той же migration. Он проверяет работу SDK, UI, создания и повторной загрузки, но не выдаётся за внешнюю Supabase-проверку.
